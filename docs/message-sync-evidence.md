# Message synchronization evidence

The pinned Web `messageSyncDomain.ts` uses a sparse `messages` domain: a server-wide message sequence is not contiguous inside one channel. Its compatibility domain consumes `message:new`; the established socket `sync:resume` transport owns reconnect replay. It does not invent a messages snapshot/difference HTTP endpoint.

`MessageSync` ports that consumer to `raft_sync`. `WorkspaceController` evaluates the mounted `sync_core_messages_v0` capability for the current workspace and rejects stale flag responses across account/workspace changes. Enabled ingress deduplicates/regression-checks new channel facts; unresolved/off ingress preserves the legacy delivery path. Positive safe numeric sequences and canonical uint64 strings remain exact at the boundary. Missing sequences retain the source's fallback.

Task/status `message:updated` facts merge only into existing loaded messages. They preserve absent text, sender, attachment and sequence fields, and use the canonical shared-null-preserve policy for `commentRef`. A partial update cannot manufacture a message. Channel revocation clears both the visible ledger and the pure core's channel scope; later revoked ingress is rejected.

Baseline validation before the reply/preference additions: 31 sync package tests, including 18 pinned TypeScript reducer equivalence scenarios and four message-domain boundary tests; three controller tests exercise real event ingestion, flag-off behavior and late capability rejection. Nine send/mention tests cover retry identity, immutable mentions, latest-history navigation, old success and old failure fencing, intentional current-channel refresh, and durable conversion pause/recovery. The expanded native suite owns reconnect/idempotency/read/revocation proof separately.

The experimental Activity TypeSpec cutover remains distinct from this message compatibility domain. The mounted Web's Activity cutover is off unless its build environment explicitly resolves `VITE_ACTIVITY_SYNC_CORE_MODE` to `shadow` or `on`; the current client uses the mounted inbox/read-state APIs. A passing pure reducer does not establish that experimental transport's platform parity.

## Enabled thread-replies compatibility domain

The pinned Web `socketBridge.ts` consumes producer-eligible `thread:updated` frames through `threadRepliesSyncDomain.ts` regardless of the broader messages rollout flag. The mounted message-service producers emit `message-service.thread-replies-window.v1` with a message/replies/sync-scope envelope and a matching parent conversation anchor. The native `ThreadRepliesSync` adapter now validates that contract, isolates server/principal/parent/thread scopes, applies sparse duplicate/regression checks, and folds an immutable newest-last latest-three preview. System replies advance the count/seam without entering the visible preview. Unknown producers retain the legacy fixed-snapshot-seam path; count-only legacy summaries remain available. Known malformed canonical producers fail closed.

Bundled `threadSummariesByParentMessageId.latestReplies` snapshots hydrate the same domain. At an equal watermark a strictly richer, nonregressing window may replace a provisional live window. The canonical producer epoch is retained beside compatibility snapshots whose wire epoch is absent. A new epoch coalesces a bounded pending window and rebaselines using the exact mounted pair: `GET /messages/channel/:threadChannelId?limit=3` and `GET /channels/:parentChannelId/threads/:parentMessageId`. The response must identify the requested thread and provide its count; snapshot reply projection uses the source sender-name/display-name fallbacks and null avatar. Pending frames replay only after an accepted snapshot. Superseded requests, changed roles/accounts/workspaces, revoked channels and disposed controllers cannot reapply private summaries.

Accepted live and rebaseline summaries request the existing `GET /channels/unread?summary=1` refresh, including when the member receives no separate `message:new`. Duplicate, dropped and pending frames do not issue that refresh. This is a source compatibility adapter, not a new replies HTTP protocol. The application uses the folded `latestReplies` for the inline thread preview and its real focused-thread navigation.

## Configurable notification-preference domain

The controller evaluates the real `sync_core_notification_prefs_v0` key alongside `sync_core_messages_v0` through the mounted feature evaluator. False, unknown, failed and stale authority evaluations do not enable the preference core. The mounted `notification_prefs:updated` payload contains `serverId`, `scopeId`, `prefs` and an optional nonnegative safe-integer `prefsVersion`. Channel activity-mute and server push-mute updates use separate sparse scopes. Equal/older versions are dropped by the enabled core; a missing version retains the source legacy path. Current server/channel projections also retain their version guards when the core is off. Wrong-server and revoked-channel updates cannot affect the selected workspace. No invented preference snapshot/difference route is used.

Source pointers: `packages/web/src/store/notificationPrefsSyncDomain.ts`, `notificationPrefsSyncFeatureFlag.ts`, `channelDomain.ts` and `socketBridge.ts`. The local feature evaluation does not establish a configured enabled rollout; the client supports the actual conditional path and its legacy behavior.
