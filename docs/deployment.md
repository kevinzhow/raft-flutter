# Self-deploy

This repository builds the **client**. You need a Raft server for it to talk to; run your own from [raft-source](https://github.com/botiverse/raft-source) (`pnpm install && ./raftdev start`, which needs Node 24, pnpm and Docker; see that repository). The client does not need a server-side change.

## Point the client at your server

- Login screen: the server origin is editable (scheme `http` or `https` and host only, no path, such as `https://raft.example.com`). Prefer HTTPS.
- Compile-time default: `--dart-define=RAFT_ORIGIN=<origin>` (default `https://api.raft.build`, the official API). Related defines: `RAFT_FRONTEND_ORIGIN` (the Web frontend origin used for browser hand-off and content links; only honoured for the API named by `RAFT_ORIGIN`. Without it, the official API `https://api.raft.build` links to `https://app.raft.build` (`ContentLinks.officialWebOrigins`) and any other server links to its own origin), `RAFT_DEPLOYMENT_ENV` (`production` default; `staging` and `slockdev` switch the Raft Computer install commands), `RAFT_APP_VERSION` (label shown in settings). `tool/release.py` passes `RAFT_ORIGIN`, `RAFT_FRONTEND_ORIGIN`, `RAFT_DEPLOYMENT_ENV=production`, `RAFT_COMMIT_SHA` and the version/build number to every release build, and refuses to build when one is missing or not the official value; the optional repository variable `RAFT_FEEDBACK_EXPORT_URL` enables Report Issue. Do not pass credentials or test fixtures as defines.
- Android blocks cleartext HTTP except for three development hosts (`network_security_config.xml`); a public deployment must use HTTPS. Android backup is disabled and local state is excluded from cloud and device-transfer backups.
- The `raft:` URL scheme (OAuth callback and content links) is registered on Android, macOS, iOS and in the Linux desktop entry.

## Raft HTTPS links and OS association

The client accepts narrowly scoped HTTPS entries by default (`RAFT_APP_LINKS=false` explicitly disables receiving). Native entry registration is present for Android and iOS, with opt-in signed macOS entitlements prepared; this does **not** establish OS verification or signing readiness. The accepted paths are `/s/<slug>/channel|dm/<id>` with validated `msg`/`thread` anchors, `/join/<token>` and `/integration-invites/<token>`. Unknown paths, credentials, non-default ports, malformed/duplicate anchors, fragments and foreign origins are rejected. `raft://v1/integration-invites/<token>` remains usable independently of HTTPS association. Tokens only select an invitation page; the active account/coordinator still validates the invitation and explicitly authorizes installation.

`RAFT_FRONTEND_ORIGIN`, bound to `RAFT_ORIGIN`, permits an exact custom frontend origin; it never permits arbitrary hosts or changes the signed-in coordinator. Android derives its single registered HTTPS hostname from that frontend define (default `app.raft.build`) and disables the dedicated alias when `RAFT_APP_LINKS=false`. Apple custom builds must also set `RAFT_APP_LINK_HOST` to that same hostname in Xcode settings and provide the matching signed entitlement and domain files. A development build using an HTTP frontend must set `RAFT_APP_LINKS=false`; an HTTP origin is not an App Link. The official legacy frontend is accepted when explicitly delivered to the client, but is not registered as a second verified host: its current association URLs redirect, which is insufficient for OS verification. Staging and wildcard hosts are not registered.

The domain owner must serve the following over HTTPS, directly (no redirects), using `application/json`:

- `/.well-known/assetlinks.json`: append the statement in [the Android association template](../packaging/app-links/assetlinks.json) to existing statements. It binds **this client's** package `app.raft.raft_flutter` to the public release certificate verified from v1.21.23+19 (`56:5C:29:87:7E:7E:DC:82:FF:44:9B:8F:44:06:E7:B9:8E:F2:FC:E1:1E:67:A2:55:5D:14:2B:E1:30:6C:CD:33`). Recheck the actual APK signer before publishing or after a signing-key change. Do not list debug/isolated keys, replace other clients' statements, or change this client's package identity to borrow another app's association.
- `/.well-known/apple-app-site-association`: merge a completed [Apple template](../packaging/app-links/apple-app-site-association.template). It is intentionally **not deployable**: `<OWNER_VERIFIED_APP_ID_PREFIX>` must come from the actual signed application's `application-identifier` entitlement, not an inferred team or another client's AASA entry. This client bundle is `app.raft.raftFlutter`. Configure the signing team/provisioning profile and `com.apple.developer.associated-domains` capability for the actual iOS/macOS App ID. The current projects specify no development team; released macOS artifacts are ad-hoc, so Apple Universal Links are not proven ready. To preserve those existing builds, the default Mac entitlements stay unchanged. Once a valid profile authorizes this capability, select `Runner/DebugProfileAppLinks.entitlements` or `Runner/ReleaseAppLinks.entitlements` with the Xcode `CODE_SIGN_ENTITLEMENTS` setting. Do not add restricted capabilities to an ad-hoc signature or infer a provisioning profile from a public AASA file. Apple [TN3125](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles) explains this signing boundary.

On 2026-11-04, direct public reads of `app.raft.build` returned valid association JSON for a **different** client (`build.raft.app`), not this client's package/bundle. Default HTTP user agents returned 403 while a named audit user agent returned 200; a 403 is not proof that files are missing. The legacy `app.slock.ai` URLs redirected to the canonical host. Existing entries must be preserved when adding this client. Readback does not establish what Android/Apple verification services can fetch or what an installed app resolves.

Android's existing Activity/plugin handles cold and warm intents. iOS's existing Flutter scene/plugin forwarding handles Universal Links; `FlutterDeepLinkingEnabled=false` prevents Flutter's competing default route handler, as required by the app_links plugin. macOS explicitly forwards `NSUserActivity` to `app_links`, whose plugin does not do that itself. The content coordinator retains one bounded private-invite URL until the root's `onPrivateAppInvite` handler attaches; message navigation still checks account/server membership. The root owns invitation presentation, origin checks, sign-in continuation and installation. Before shipping, verify real cold/warm OS taps, signed-out recovery and rejection cases on the exact signed application. A parser/widget success is not native OS acceptance.

Linux continues its existing `raft:` registration and single-instance argument forwarding. It can receive an explicitly delivered allowed HTTPS URL, but does **not** register itself as the global HTTPS handler/default browser: Linux has no equivalent standard per-domain Android/Apple association. Windows host registration belongs to the Windows maintainer and is not changed here.

## Build release artifacts

Run from `apps/raft_flutter` with `../../tool/flutter` and the pinned SDK. Release builds use `--target=lib/main.dart` (the default) and must not include the test defines used by the native test scripts.

```sh
../../tool/flutter build apk --release --dart-define=RAFT_ORIGIN=https://raft.example.com           # Android universal APK
../../tool/flutter build apk --release --split-per-abi --target-platform android-arm64 --build-number <n>  # ARM64 split APK
../../tool/flutter build linux --release                                                            # Linux x86_64; install system development packages first
../../tool/flutter build macos --release                                                            # macOS app Raft.app (arm64)
```

Linux uses distribution WebKitGTK 4.1, GTK3 and libmpv; see [system runtime prerequisites](linux-media-runtime.md). The browser engine and system media libraries are not built or bundled by this project.

## Signing and packaging

GitHub-hosted automatic builds and version-tag releases are described in
[Release CI](release-ci.md). Windows x64 is enabled first; Android, Linux and macOS
builders can be tested manually and enabled through a shared platform configuration.

- **Android**: local acceptance builds still use the **debug key**. CI uses the environment-based release signing configuration and requires a persistent keystore through GitHub secrets (see [Release CI](release-ci.md)); those secrets stay outside the repository. The application id is `app.raft.raft_flutter`. Updating an installed app needs the same signing key and a higher version code; use `tool/android-install --device <serial> --apk <arm64.apk> --check-only` and then `--launch`, which checks identity, architecture, version and signature and never uninstalls or clears data. CI does not perform store submission.
- **Linux**: `tool/build-deliverables` is the local acceptance packager. It requires a passing `tool/check-project` and native runs for the same source hash, then builds the Linux bundle and APK, rewrites ELF RPATHs to be relocatable with a pinned local `patchelf`, checks dependencies, and writes `build/deliverables/raft-flutter-linux-x64.tar.gz`, `raft-flutter-android.apk`, `CHECKSUMS.txt` and `build-manifest.json`. The bundle needs a compatible glibc, GTK and graphics drivers, and `poppler-utils` for PDF preview. An example desktop entry for the `raft:` scheme is in `linux/packaging/`. Media libraries include GPL components; read [Linux media runtime](linux-media-runtime.md) before redistributing.
- **macOS**: sandboxed (entitlements in `macos/Runner/`), local development signing only. Developer ID signing, notarization and DMG/store packaging are not set up ([macOS evidence](macos-evidence.md)).
- **iOS**: no signing team, provisioning, push or release setup; configure signing in Xcode on a Mac. Compilation has never been verified.
- **Windows**: x64 Release builds produce the complete `apps/raft_flutter/build/windows/x64/runner/Release` directory, a portable ZIP and a per-user setup executable. Keep its DLLs, `data/`, `raft.ico` and `notification_icon.png` together. The bundle includes the MSVC runtime; notifications use the Windows system Toast API without Windows App Runtime. Run the app once from its final folder to register its current-user identity and protocol. No Authenticode signature or store package is configured. See [Windows development setup](development.md#windows) and [notification behavior](windows-notifications.md).

Verification of the delivered Android and Linux artifacts (hashes, install and relocation smoke tests, what they do not prove): [release evidence](release-evidence.md).
